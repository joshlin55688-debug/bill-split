## 1. 設計目標與取捨

### 為什麼選「單一 HTML 檔」？
- **目標**：使用者雙擊就能玩，不裝任何東西、不用 build、可離線。
- **取捨**：放棄框架（React/Vue）、放棄模組化拆檔。換來零依賴、零部署、好備份。
- **代價**：檔案會變大、所有狀態靠全域 `S` 物件，後期若功能爆量會難維護。
  → **未來若功能變多，建議拆成 Vite + 模組**，再用 esbuild 打包回單檔。

### 為什麼用 `localStorage` 而非 IndexedDB？
- 存檔資料量極小（一個 JSON），`localStorage` 足夠且 API 最簡單。
- **限制**：清除瀏覽器資料 = 存檔消失；換瀏覽器/裝置不同步。
  → 未來若要跨裝置，需後端帳號系統或匯出/匯入 JSON 字串功能。

## 2. 架構筆記

### 2.1 全域狀態 `S`
所有遊戲進度集中在一個物件，存讀檔就是 `JSON.stringify(S)` / `JSON.parse`。

```
S = {
  steps, totalSteps,        // 當前可用步數 / 累積總步數
  day, dayProgress,         // 天數 / 當天進度（滿 120 換日）
  ess: {七色精華數量},
  pikmin: [ {id,type,growth,intimacy,loveLv,accessory,nick,busyUntil} ],
  seeds: [ {type} ],        // 場上待拔花苗
  expeditions: [ {expId,members,until} ],  // 進行中探險
  expDone, unlockedArea, postcards,
  decor: [ {type,accessory} ],  // 飾品皮克敏圖鑑
  achGot: [成就id], story, lastTs
}
```

> **教訓**：`load()` 內有「migration」邏輯，把 `freshState()` 缺少的欄位補回 `S`。
> 這是為了「改版加新欄位時，舊存檔不會壞」。**任何加新欄位都要記得放進 `freshState()`**，否則舊存檔讀進來該欄位是 `undefined`，容易 crash。

### 2.2 資料驅動設計（重要）
所有「內容」都抽成設定表，邏輯讀表運作，**加內容不用改邏輯**：
- `TYPES`：7 種皮克敏（名字、顏色、屬性、力量、速度、性格台詞、特殊能力 break/fly、喜好天氣）。
- `GROW`：葉子/花苞/花朵的力量倍率（1 / 1.4 / 2）。
- `EXPEDITIONS`：探險任務（力量門檻、耗時、獎勵、區域、是否需破壞型/飛行型）。
- `ACHIEVEMENTS`：成就（用 `chk: s => 條件` 函式判定，超彈性）。
- `ACCESSORIES`：飾品 emoji 清單。

→ **想加新皮克敏 / 新任務 / 新成就，只要往對應陣列加一筆即可。**

### 2.3 渲染方式
- 沒有用框架，靠 `renderXxx()` 函式重建該分頁的 `innerHTML`。
- 皮克敏立繪是純 CSS（水滴身體 + 眼睛 + 莖 + emoji 頭飾），用 `pkSprite()` / `pkSpriteMini()` 生成。
- 主迴圈 `setInterval(tick,1000)`：每秒檢查探險是否完成、刷新探險分頁倒數。
- `setInterval(save,15000)`：每 15 秒自動存檔；`beforeunload` 再存一次。

## 4. 踩過的坑與修正（最有價值的部分）

### 🐛 Bug 1：重置存檔失效 ❌→✅
- **現象**：按「重置存檔」後 `localStorage.removeItem()` + `location.reload()`，但重載後存檔還在。
- **原因**：`window.addEventListener('beforeunload', save)` 會在 reload 觸發前把**記憶體裡的舊狀態**重新寫回 `localStorage`，等於白刪。
- **修正**：加一個 `_noSave` 旗標，`save()` 開頭 `if(_noSave) return;`。重置時先 `_noSave=true` 再刪、再 reload。
- **教訓**：**只要有 `beforeunload` 自動存檔，任何「刪檔後重載」的流程都要先關掉自動存檔**，否則必定被覆蓋。這是這類遊戲的通用陷阱。

### 🐛 Bug 2：測試時 `feed(undefined)` 崩潰
- **現象**：序章選完選項後直接呼叫 `feed(red)` 報 `Cannot read properties of undefined`。
- **原因**：新玩家序章時，小紅其實還是**場上的花苗(seed)**，尚未 `pluckSeed()` 變成 `pikmin`。所以 `S.pikmin.find(type==='red')` 是 `undefined`。
- **修正/認知**：這其實是**測試腳本的順序問題**，非遊戲 bug。但暴露了一個設計細節：
  序章旁白寫「你終於把我拔出來了」，但實際上玩家還沒拔 → **敘事與狀態有輕微落差**。
  → 未來可考慮：序章開場直接自動拔出小紅，讓敘事與畫面一致。

### ⚠️ 注意點：測試污染
- 用 `preview_eval` 直接呼叫遊戲函式來快速測試很方便，但會把測試資料寫進 `localStorage`，
  導致下次「新玩家」流程被污染（步數、皮克敏殘留）。
- **作法**：測試完務必 `_noSave=true; localStorage.removeItem(...)` 清乾淨，再交付。

## 7. 如果要重做 / 接手，建議怎麼開始

1. **先讀 `TYPES`、`EXPEDITIONS`、`ACHIEVEMENTS` 三張表**，就懂八成內容。
2. **狀態流向**：使用者操作 → 改 `S` → 呼叫 `renderXxx()` + `save()`。所有函式都遵守這個模式。
3. **加新內容**：往設定表加一筆，必要時在 `freshState()` 補欄位、`load()` 會自動 migrate。
4. **改數值**：集中在第 5 節列的常數（`WALK_GAIN`、`PLUCK_COST`、`GROW` 倍率…）。
5. **測試**：本地 `npx serve Web-game-dev`，開瀏覽器。測完記得清 `localStorage`。
6. **若功能膨脹到單檔難維護** → 拆 Vite 專案，但保留「打包成單檔」的能力（使用者習慣雙擊開）。

## 8. 「自動追加」是怎麼運作的

本檔最末的 **「📌 自動開發日誌」** 由 git hook 自動維護：

- **觸發時機**：每次 `git commit`，且該次提交有動到 `Web-game-dev/`（DEVLOG 自己不算，避免迴圈）。
- **hook 位置**：`.git/hooks/post-commit`（本機專屬，不會被 commit、不會分享給別人）。
- **追加內容**：日期時間、commit 短雜湊、commit 訊息、變更的檔案清單。
- **追加位置**：永遠加在檔案**最末**（時間順序，最舊在上、最新在下）。
- **注意**：hook 在 commit 完成「之後」才寫入，所以這筆日誌會變成「未提交的變動」，
  會在你**下一次 commit** 時一起被收進版本庫（有一筆的時間差，屬正常現象）。

> 想手動補寫詳細紀錄（例如某個失敗的嘗試、設計思路）時，
> 直接在下面照同樣格式加一段即可，不必等 commit。
>
> ⚠️ **請不要在「📌 自動開發日誌」這行標題之後，再新增其他「章節標題」**，
> 否則 hook 追加的內容會跑到那些章節後面，順序會亂。新章節請加在本節以上。
